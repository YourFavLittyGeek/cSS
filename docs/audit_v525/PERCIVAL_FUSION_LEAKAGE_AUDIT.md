## 1. Executive Summary & Leakage Verdict

In machine learning pipelines for neuroimaging, data leakage is the most prevalent cause of spuriously inflated performance. Leakage occurs when information from test or validation subjects inadvertently influences feature scaling, model training, or hyperparameter selection.

### Forensic Verdict:
- **v5.24 Critical Defect Confirmed:** A severe form of **indirect validation leakage** existed in Percival v5.24. In v5.24, second-level Fusion models fitted during outer cross-validation used out-of-fold predictions (`img_oof[tr]`) generated by outer models that had been trained on data partitions containing the held-out validation fold `te`.
- **v5.25 Nested Cross-Fitting Fix Verified:** Percival v5.25 completely eliminates this defect by implementing true **nested cross-fitting**. Within each outer training fold $tr$, an inner 3-fold patient-grouped cross-validation produces level-0 predictions solely from subsets of $tr$. The outer validation fold $te$ is completely isolated.
- **Patient-Level Partitioning Invariant Holds:** Partitioning is strictly grouped by patient ID (using a deterministic SHA-256 salted hash), guaranteeing that multiple MRI studies from the same subject never straddle training, validation, or test cohorts.

## 2. Forensic Analysis of the v5.24 Leakage Defect

### 2.1 The Mechanism of Indirect Leakage
In stacked generalization (stacking) and multi-modal fusion, level-1 meta-learners must be trained on out-of-sample predictions of level-0 models.

In v5.24, the execution order was:
1. Outer 5-fold CV was executed across all development patients to produce a cohort-wide vector `img_oof`.
2. For outer fold $k \in \{0, \dots, 4\}$ with training set $tr_k$ and validation set $te_k$:
   - To fit the Fusion model on $tr_k$, the algorithm extracted `img_oof[tr_k]`.
   - Consider patient $A \in tr_k$ who belonged to outer fold $j$ ($j \ne k$).
   - The value `img_oof[A]` was produced by an Image ML model trained on all folds except $j$ — which included fold $k$ ($te_k$!).
   - Therefore, the features fed to the Fusion model during fold $k$ training were generated by models trained directly on the validation subjects of fold $k$.

### 2.2 Mathematical Proof of Information Flow in v5.24
Let $\mathcal{D} = \bigcup_{m=0}^{K-1} \mathcal{F}_m$.
For outer fold $k$, validation set is $\mathcal{F}_k$, training set is $\mathcal{D}_{-k} = \bigcup_{m \ne k} \mathcal{F}_m$.
In v5.24:
$$\forall j \ne k, \quad \hat{y}_{\text{img}}(x_i) \quad \text{for } x_i \in \mathcal{F}_j \quad \text{was produced by } \mathcal{M}_{\text{img}}^{(-j)} = \text{Train}\left(\mathcal{D} \setminus \mathcal{F}_j\right)$$
Because $\mathcal{F}_k \subset (\mathcal{D} \setminus \mathcal{F}_j)$ for all $j \ne k$:
$$\mathcal{M}_{\text{img}}^{(-j)} \text{ was trained on } \mathcal{F}_k \implies \hat{y}_{\text{img}}(x_i) \text{ depends on } y(\mathcal{F}_k)$$
When the Fusion model $\mathcal{M}_{\text{fusion}}^{(k)}$ was fitted on $\{\hat{y}_{\text{img}}(x_i) : x_i \in \mathcal{D}_{-k}\}$, its parameters $\mathbf{W}_{\text{fusion}}^{(k)}$ became explicit functions of $\mathcal{F}_k$:
$$\frac{\partial \mathbf{W}_{\text{fusion}}^{(k)}}{\partial y(\mathcal{F}_k)} \ne 0$$
This violated the fundamental assumption of cross-validation independence: the validation score on $\mathcal{F}_k$ was optimistically biased.

### 3.1 Implementation in `meta.py` (lines 318–346)
In v5.25, the outer fold loop is completely restructured:
```python
for i, (tr, te) in enumerate(F):
    assert not set(g[tr]) & set(g[te]), "patient in both the training and the held-out fold"
    R = [rows[j] for j in tr]; T = [rows[j] for j in te]

    # Inner patient-grouped CV strictly within tr:

    for itr, ite in folds(g[tr], 3, seed + 31 + i):

        if mi is not None: inner[ite] = mi.logit(Xc[tr][ite])

        inner_img[b] = _fit_image(ik, M[tr][a], y[tr][a], g[tr][a], seed + 31 + i, cnn_epochs).logit_tta(M[tr][b])[0]
    
    # Fusion is fitted ONLY on the inner OOF predictions of tr:
    f = _pl_fit(_fusion_X(kd, Xc[tr][fin], inner_img[fin], inner[fin]), y[tr][fin], g[tr][fin], w[tr][fin], _fusion_cols(kd))
    
    # Validation predictions for te use models trained on the whole of tr:
    fu[kd][te[hte]] = f.logit(_fusion_X(kd, Xc[te][hte], img_oof[te][hte], P["char"][hte]))
```

### 3.2 Formal Verification Checklist
1. **Outer Isolation:** Does $te$ participate in the inner loop?
   - `folds(g[tr], 3)` partitions only `g[tr]`. $te$ is never passed into the inner loop. **PASS.**
2. **Inner Feature Production:** Are `inner_img` and `inner` computed out-of-sample within $tr$?
   - Yes, `ite` is held out from `itr` within $tr$. No training sample is predicted by its own model. **PASS.**
3. **Outer Model Application:** Are `img_oof[te]` and `P["char"][te]` computed without seeing $te$?
   - `img_oof[te]` is produced by an Image ML model trained on $tr$.
   - `P["char"][te]` is produced by a tabular model trained on $tr$.
   - Neither model had access to any subject in $te$. **PASS.**
4. **Patient Hash Invariance:**
   - In `test_assignment(patient, fraction, salt)`, a 64-bit integer derived from SHA-256 partition salt determines development vs. test status.
   - For any patient with multiple longitudinal acquisitions, all scans share the same patient ID, ensuring $100\%$ co-partitioning. **PASS.**
